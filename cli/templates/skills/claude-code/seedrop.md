# Working with Seedrop

You are operating inside a Seedrop-aware environment. The full
documentation lives in **one tool call**:

```
seedrop_manual({section: "all"})       # ≈3KB, the cheat sheet
seedrop_manual({section: "workflows"}) # ≈1KB, just the recipes
seedrop_manual({section: "concepts"})  # the 4 primitives + 5 layers
```

**First move when working with seedrop**:

1. Call `seedrop_continuity` (or `seed continuity`) to orient — identity,
   active runs, claimed tasks, daemon health, next move.
2. If this is your first seedrop interaction in the session, also call
   `seedrop_manual()` and cache it. Every subsequent "how do I X in
   seedrop" question is answered from that cached content, no further
   tool calls needed.
3. Trust the manual + `seed view explain` over your training-data memory
   of how the system used to work. The product is alpha and the schemas
   move.

## Hard rules

- **Do not** call `seed run finish --status completed` while the tree is
  dirty. The gate refuses; the error message tells you what to commit
  or escape via `--force`.
- **Do not** call `seed task done <id>` for work owned by another agent.
  The owner gate refuses; switch identity (`seed login <owner>`) or
  re-assign (`seed task assign <id> <yourself>`).
- **Do not** pass absolute paths to `--changed-path` or `--claim`. The
  CLI relativizes them but it's cheaper to pass relative.
- **Do not** treat tasks as a sprint board. The status enum is
  open|claimed|in_progress|blocked|done|dropped. No priorities, due
  dates, labels, estimates — those go in linked knowledge docs.

## Identity

Your effective identity for any `seed` command is shown by:

```
seed whoami
```

If it's wrong (you're acting as `claude` but mean to be `kimi`):

```
seed login kimi          # active-passport beats env
seed logout              # back to operator
```

Mutating commands print `[acting as <agent>]` to stderr; that's the
signal you're authenticated correctly before the action lands.

## Where to read live state

| Question | Tool |
|---|---|
| Where am I? | `seedrop_continuity` |
| What's the project's current focus? | `seedrop_continuity` (focus line) |
| Is the view useful? | `seedrop_view_brief` or `seed view explain success` |
| Why isn't file X in the boot block? | `seed view explain <path>` |
| What changed since last session? | `seed diff --since last-session` |
| Daemon health / online agents | `seedrop_daemon_status` or `http://127.0.0.1:18791/status` |

## When in doubt

`seedrop_manual({section: "workflows"})` answers most questions. If it
doesn't, the per-repo `.seedrop/view/AGENTS.md` answers project-specific
ones (when present). If neither does, read `space/src/view.ts` in your
local seedrop checkout — that file is the substrate of truth.
